# 雲端儲存系統壓力測試計畫(100 併發使用者)

## 1. 目的與範圍
驗證雲端儲存服務在 **100 位使用者同時在線** 時,執行上傳/下載檔案、影片串流、照片上傳並產生縮圖等混合負載下,是否滿足效能、穩定性與資源使用目標,並找出瓶頸。

**範圍內**:API / 物件儲存 / 縮圖(影像處理)worker / 影片串流(HTTP Range)/ 資料庫 / 快取 / 網路。
**範圍外**:第三方 CDN 本身、客戶端 UI 渲染效能、登入供應商(SSO)容量。

## 2. 測試環境與前置條件
| 項目 | 要求 |
|---|---|
| 環境 | 與正式環境同規格的 staging(禁止直接打 production) |
| 壓測機 | 獨立機器(≥4 vCPU / 8GB),與被測 server 同區網,避免壓測機成為瓶頸 |
| 測試帳號 | 100 組(`user001`~`user100`)+ 1 組 admin,預先建立 |
| 測試資料 | 照片 5,000 張(1~8MB)、影片 50 部(50MB~1GB,含 H.264/MP4)、一般檔案 1KB~500MB |
| 工具 | k6(產生負載);伺服器資源直接看「雲端平台後台的監控圖表」或「主機的工作管理員/效能監視畫面」,人工看結果並記錄 |
| 時鐘 | 壓測機與 server 皆 NTP 同步,方便對齊時間序列 |

## 3. 使用者角色定義(100 user 比例)
測試把 100 位 user 分成 3 種角色(約 34 / 33 / 33 人),同時進行、互相搶資源,模擬真實混合使用情境。

| 角色ID | 角色 | user 數 | 一輪完整動作(依序) | 動作之間的停頓 | 主要考驗的資源 |
|---|---|---|---|---|---|
| R1 | 檔案使用者 | 34 | 1.登入 2.看檔案列表 3.上傳一個檔案(1MB 60%、50MB 30%、500MB 10%) 4.下載剛上傳的檔案並檢查內容有沒有損毀 | 1~3 秒 | 上傳/下載頻寬、硬碟寫入、記憶體 |
| R2 | 影片觀看者 | 33 | 1.登入 2.看影片列表 3.選一部影片 4.連續分段播放約 30~60 秒(每段 2MB) 5.偶爾拖動進度條跳到別處 | 每段間隔 2~4 秒(模擬邊看邊載) | 網路出去流量、硬碟讀取 |
| R3 | 照片上傳者 | 33 | 1.登入 2.上傳一張 3~8MB 照片 3.等待系統產生縮圖(最多等 30 秒) 4.取得小/中/大三種尺寸縮圖 | 2~5 秒 | 縮圖處理(CPU)、排隊數量、硬碟 |

**一輪**:一個 user 把自己角色的上述動作從頭做到尾一次。做完停頓一下再開始下一輪,直到測試時間結束。
**三種角色各一輪**:三種角色都至少完整做過一次,用來確認每項功能都能用(例如冒煙測試 TC-01)。
**混合執行**:三種角色同時進行,不是一種做完才換下一種。

## 4. 測試情境(口語說明)
| ID | 在測什麼 | 人數 | 時間 | 怎樣算通過 |
|---|---|---|---|---|
| TC-01 | 先小規模試跑,確認功能都正常 | 5 人 | 2 分鐘 | 一個錯誤都沒有 |
| TC-03 | 100 人同時操作 | 100 人 | 30 分鐘 | 速度與資源都符合第 6 節 |
| TC-06 | 長時間連續操作,看會不會越用越差 | 100 人 | 4~8 小時 | 記憶體、連線數、回應速度全程穩定 |
| TC-07 | 大量上傳照片,看縮圖做不做得完 | 100 人(都傳照片) | 15 分鐘 | 縮圖都有做出來,排隊數量不會一直增加 |
| TC-08 | 100 人同時上傳大檔案(500MB) | 100 人 | 10 分鐘 | 沒有失敗,記憶體不會暴增 |
| TC-09 | 100 人同時看影片 | 100 人 | 15 分鐘 | 影片順暢不卡頓,網路沒被塞滿 |
| TC-10 | 服務臨時出問題後能不能自己恢復 | 100 人 | 15 分鐘 | 問題排除後恢復正常,資料沒壞 |
| TC-11 | 檔案有沒有損毀、縮圖有沒有漏做 | 100 人 | 全程 | 檔案內容 100% 一致,縮圖數量不少 |

> 完整的用例清單(含單一功能的用例)見 `test-cases.csv`。

## 5. 監控項目(人工觀察,口語說明)
不需要輸入任何指令。請打開雲端平台(AWS / GCP / Azure / 其他)後台的伺服器監控頁面,或請維運同仁提供監控畫面,**用眼睛看圖表、把數字記在 `manual-record-sheet.csv`**。每次記錄請寫下時間。

| 要看什麼 | 白話意思 | 怎麼判斷有問題 |
|---|---|---|
| 處理器忙碌程度(CPU) | 伺服器現在有多忙 | 長時間超過 70% 偏高,超過 90% 危險 |
| 記憶體剩餘 | 還剩多少記憶體可用 | 剩不到 20%,或曲線一路往上不回頭(疑似洩漏) |
| 網路流量(進/出) | 每秒收到/送出多少資料 | 接近網路頻寬上限(超過 80%) |
| 硬碟忙碌程度 | 硬碟讀寫是否塞車 | 接近 100% 或讀寫等待明顯變久 |
| 連線數 | 同時有多少人連著 | 突然暴增或一直累積不下降 |
| 縮圖排隊數量 | 等著做縮圖的照片有多少 | 一直增加、不見消化 |
| 當機或被強制關閉 | 服務有沒有掛掉重啟 | 出現「記憶體不足被終止」等警示 |
| 用戶端結果(k6 報告) | 使用者實際感受到多快、多少失敗 | 對照第 6 節的目標值 |

> 若沒有監控後台,可請維運/工程同仁協助截圖(每個時間點一張),測試後依截圖填表。

## 6. 通過標準(100 人同時操作,TC-03)
| 項目 | 目標(白話) |
|---|---|
| 一般操作(看列表、查資料) | 95% 的操作在 0.5 秒內完成 |
| 小檔案(1MB 以內)上傳/下載 | 95% 在 2 秒內完成 |
| 50MB 檔案上傳/下載 | 95% 在 20 秒內完成 |
| 影片按下播放到開始出畫面 | 95% 在 1 秒內 |
| 縮圖載入(上傳後取得縮圖) | 95% 在 0.3 秒內 |
| 照片上傳後到縮圖做好 | 95% 在 10 秒內 |
| 失敗比例 | 低於 1% |
| 處理器忙碌程度 | 平均低於 70%,最高不超過 90% |
| 記憶體 | 剩餘多於 20%,不用借硬碟當記憶體,沒有被強制關閉 |
| 網路 | 用量低於上限的 80%,封包重傳很少 |
| 硬碟 | 忙碌程度低於 80%,讀寫等待不明顯 |
| 檔案完整性 | 上傳前後內容 100% 一致 |

> 「95%」的意思是:100 次操作裡有 95 次達標。目標值是建議預設,請依實際需求調整 `cloud-storage.k6.js` 裡的 `thresholds`。

## 7. 執行步驟
1. 部署與正式相同版本至 staging,清空快取,記錄版本/設定(instance 規格、worker 數、連線池)。
2. 打開伺服器的監控頁面(雲端後台圖表或維運提供的畫面),保持畫面開著,並把時間範圍設為「最近 1 小時、自動更新」。
3. 在壓測機執行:
   ```bash
   k6 run -e BASE_URL=https://staging.example.com \
          -e SCENARIO=load \
          --summary-export results/run1/k6-summary.json \
          --out json=results/run1/k6-raw.json \
          cloud-storage.k6.js
   ```
   `SCENARIO` 可選:`smoke`(5 user,2 分鐘)| `load`(100 user,30 分鐘)| `soak`(100 user,4 小時)。所有 user 一開始就同時操作,沒有逐步增加人數的階段。
4. 結束後彙整手動記錄表與 k6 報告,繪圖(Excel 即可)。

**手動監控時間點(建議)**:測試開始前(基線)、開始後 1 分鐘、之後每 5 分鐘、測試結束後 2 分鐘;每次記錄時間,以及處理器忙碌程度、記憶體剩餘、網路流量、硬碟忙碌程度、連線數。出現延遲突增或錯誤時,立即多記一筆。
5. 比對 §6 準則,填寫 §9 報告。

## 8. 風險與注意事項
- 壓測前通知相關團隊,避免觸發告警/配額/計費;雲端儲存請確認出站流量費用。
- 測試資料需獨立 bucket/租戶,測後清理。
- 壓測機本身 CPU/網路若飽和會造成假性延遲,請同時監控壓測機。
- 影片/大檔測試可能先打滿頻寬,需分辨是「應用瓶頸」或「網路上限」。
- 先 smoke 再逐步加壓;異常即中止(錯誤率 >20% 連續 1 分鐘自動 abort,已設定於 k6 thresholds)。

## 9. 報告模板
- 測試日期 / 版本 / 環境規格
- 各情境結果表(人數、每秒操作次數、回應速度分布、失敗比例、傳輸量)
- 資源變化:處理器、記憶體、網路、硬碟(並與回應變慢的時間點對照)
- 卡關分析(哪個資源最先被用滿)與證據
- 缺陷清單與優化建議(例:縮圖 worker 水平擴充、上傳串流化、CDN 快取、連線池調整)
- 容量結論:目前架構可支撐的最大併發與建議安全水位(≤70%)

## 10. 需依實際系統調整的項目
`cloud-storage.k6.js` 內的 API 路徑(`/api/login`、`/api/files`、`/api/photos`…)為假設的範例,請依實際介面修改 `API` 常數與驗證方式。
